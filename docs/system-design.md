# KURALIVO — System Design

**Status:** Logical reference architecture. Components are proposals until verified in code and deployment.

## Design stance
Use the smallest architecture that supports the content loop. The first version can run manually with Markdown templates and a tracker. If a web workspace is built, prefer a simple modular web app and managed persistence over microservices.

## Logical components
1. **Workspace UI** — projects, briefs, editor, review, export, results.
2. **Application/API layer** — validates inputs, enforces project ownership, manages state transitions.
3. **Content workflow service** — assembles evidence and prompt context; requests AI drafts.
4. **Provider adapter** — one model provider at a time, configurable without coupling business logic to provider-specific formats.
5. **Persistence layer** — projects, evidence, assets, review records, publication and metric observations.
6. **Asset storage** — optional object storage for approved files; private by default.
7. **Telemetry/audit layer** — operational errors and important state transitions without logging secrets or unnecessary personal data.
8. **External platforms** — publishing and affiliate reporting remain manual until official, authorized integrations are implemented.

## Recommended deployment shape
- Frontend: Cloudflare Pages or an equivalent static host if consistent with the repository.
- Backend: Cloudflare Workers only if server-side validation, provider calls, or authenticated data access are required.
- Database: Cloudflare D1 or another managed SQL database if persistent multi-session data is needed.
- Asset storage: R2/private object storage only if assets need persistence.
- AI provider: adapter-based, with provider credentials stored only in server-side secrets.
- Auth: defer until private persistent multi-user access is required; if needed, use a supported auth provider and enforce server-side authorization.

This is a recommendation, not confirmation that these services are configured or deployed.

## Request flow
1. Operator submits a brief.
2. API validates fields and access.
3. Service assembles relevant project facts and evidence.
4. Provider adapter receives only necessary context.
5. AI response is parsed and schema-validated.
6. Draft is saved as unapproved.
7. UI displays the draft with source/context notes.
8. Human reviews and edits.
9. Approval transition records actor/time.
10. Export or manual publication occurs.
11. Results are recorded with source and period.

## Reliability
- Use bounded request sizes and timeouts.
- Handle provider errors with safe, recoverable messages.
- Retry only safe/idempotent operations.
- Avoid duplicate project or generation records on retries.
- Validate AI output and fall back to editable text if structured output fails.
- Keep manual export available when integrations fail.

## Security boundaries
- All provider secrets stay in server-side environment secrets.
- Browser must never receive raw API keys.
- Every persistent object must be scoped to its authorized workspace.
- Validate URLs and uploads; limit file types and size if uploads exist.
- Treat prompt content, URLs, imported product descriptions, and AI outputs as untrusted input.
- No automatic execution of code, scripts, or external actions generated by a model.
- Do not log cookies, passwords, OTPs, authorization headers, or full secrets.

## Architectural decisions to revisit
- When persistence is needed.
- Which AI provider is affordable and reliable.
- Whether account authentication is needed for the single-operator MVP.
- Which official APIs are available and authorized.
- Whether asset storage volume justifies R2.
